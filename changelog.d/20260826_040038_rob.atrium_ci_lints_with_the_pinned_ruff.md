### Fixed

- **CI now lints with the ruff this project pins, not one an action picked.**
  The dev extra pins `ruff==0.14.5` and `.pre-commit-config.yaml` pins the same
  number, so that the hook which blesses a commit and the command
  `CONTRIBUTING.md` tells you to run cannot disagree about what passes. The lint
  job was outside that agreement: it fetched ruff through
  `astral-sh/ruff-action`, which resolves a version this repository does not
  choose. The commit that added the pin said as much and left the job alone.

  This is the failure the pin exists to prevent, just relocated to the one place
  that decides whether a pull request is red. A ruff release moves formatting or
  adds a rule, and the next branch pushed goes red over code its author did not
  write and cannot reproduce in the venv the setup instructions build — and the
  diff that fails is not the diff that caused it. The job now installs
  `.[dev]` and runs what the install gave it, so the pinned version is the only
  one in play and `pyproject.toml` is the only file the number lives in.

  A test asserts the lint job installs the extra, runs both ruff commands,
  fetches ruff from no action, and names no version of its own — the last so
  that a fourth copy cannot appear while the existing two-places test goes on
  passing.
